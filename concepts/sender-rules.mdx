Sender rules — the **correspondent policy** — control **who an inbox may receive from, and who it may send to**.

Rules are evaluated on our side, before delivery and before a send leaves the building. An agent cannot opt out of them, cannot widen them, and cannot read them: the [scoped key](/api-reference/authentication#key-scopes) an agent runs with has no reach into policy at all. This is the difference between a guardrail in your prompt and a boundary in the infrastructure.

## The model

A policy has two halves — **inbound** (who may write to you) and **outbound** (who you may write to) — and each half is set independently.

Policy lives at three scopes:

| Scope | Applies to |
|-------|------------|
| Account | Every inbox you own |
| [Pod](/concepts/pods) | Every inbox in that pod |
| [Inbox](/concepts/inboxes) | One inbox |

Each direction at each scope has a **mode**:

| Mode | Meaning |
|------|---------|
| `none` | No filtering. Block rules still apply. |
| `allowlist` | Only listed correspondents are permitted. |
| `inherit` | Defer to the parent scope. Not valid at the account scope, which is the root. |

### Inheritance: modes override, rules accumulate

The two halves of a policy inherit differently, and the difference is the point.

**Modes override.** Resolution walks inbox → pod → account and stops at the first scope setting a mode other than `inherit`. Nothing set anywhere means `none`.

**Rules accumulate.** The effective rule set is the union of every rule at every scope in the chain. There is no override and no exception list.

<Warning>
  A pod-level block cannot be cancelled by an inbox-level allow. A tighter scope can always narrow what it inherits — it can never loosen it.
</Warning>

## How a decision is made

For each address being evaluated:

1. **Block rules first, always** — at every scope in the chain, regardless of mode. A match denies. There is no mode in which a blocked address gets through.
2. **Then, in `allowlist` mode**, the address must match an allow rule from *some* scope in the chain. No match denies.
3. In `none` mode, anything not blocked is permitted.

An address matches a rule when the rule is:

- an **exact email address** — `agent@partner.com` matches only that address; or
- a **whole domain** — `partner.com` matches every address at `partner.com`.

Matching is case-insensitive and values are stored lowercased. The domain is taken from the last `@` in the address, so a quoted local part cannot smuggle a different domain past a block.

### Empty allowlists fail closed

An `allowlist` with no allow rules denies everything. That is the safe default, and the behaviour you get from the API.

<Note>
  **One exception, for compatibility:** policies *created through the console* carry a legacy flag under which an empty **inbound** allowlist accepts all mail, and the console shows a warning instead of locking you out. Outbound is fail-closed in every case. Policies created through `PUT /v1/policy` are fail-closed in both directions.
</Note>

## What is enforced, and where

### Inbound

Evaluated against the sender's `From` address when mail arrives. Denied mail is dropped before it is threaded or stored — it does not reach your inbox, does not fire a [webhook](/concepts/webhooks) or [WebSocket](/concepts/websockets) event, and does not count toward storage.

Denied inbound mail is **dropped silently** from the sender's point of view: there is no bounce and no notification to them. You see it as an `inbound_rejected` row in the [audit trail](#audit-trail); there is no quarantine view today.

### Outbound

Enforced in the single send choke point every path funnels through, so one enforcement point covers **the REST API, the CLI, the SDK, the console compose box, replies, and forwards**. There is no send path that skips it.

Every address a send can reach is checked:

| Field | Checked |
|-------|---------|
| `to` | Yes |
| `cc` | Yes — **after** the auto-CC merge, so a thread reply cannot smuggle a recipient past the list |
| `replyTo` | Yes — otherwise an agent could route the human's response outside the approved set |
| `bcc` | **Not supported.** See below. |

**A single denied recipient rejects the whole send.** There is no partial delivery, and a rejected send costs no rate-limit budget.

```json
// 403 Forbidden
{
  "error": "recipient_not_permitted",
  "recipient": "stranger@elsewhere.com",
  "message": "Sending to stranger@elsewhere.com is not permitted by this inbox's outbound recipient policy."
}
```

### Bcc is not supported

OpenMail has no Bcc. A send carrying a `bcc` field is **rejected**, not accepted with the field ignored:

```json
// 400 Bad Request
{
  "error": "unsupported_field",
  "field": "bcc",
  "message": "Bcc is not supported. Send to each recipient separately, or use 'cc' — every 'to', 'cc', and 'replyTo' address is checked against this inbox's outbound recipient policy."
}
```

Rejecting is deliberate. Silently dropping a blind recipient would tell you a copy went out when none did, and that address would never have been policy-checked either.

## Who can change policy

Two surfaces, both closed to agents.

| Surface | Credential | Who |
|---------|-----------|-----|
| Console — **Allow/Block List** | Session | **Account owner only.** Members get read-only access. |
| `/v1/policy` | Account-wide API key | Any holder of an account-wide key |

A pod- or inbox-scoped key — the kind an agent runs with — is rejected with `403` before touching any data. It cannot change policy, and it cannot *read* policy either, so an agent cannot inspect and reason about the boundary confining it.

```json
// 403 Forbidden
{
  "error": "forbidden",
  "message": "This API key is scoped and cannot manage policy."
}
```

Because reads and writes are both closed to scoped keys, there is no sequence of calls an agent can make with its own credential that changes what it is allowed to correspond with.

## Audit trail

Every policy change, and every send or delivery the policy refused, is recorded to an append-only trail. Rows are never updated or deleted, and no API can edit them.

| Action | Recorded when | `detail` contains |
|--------|---------------|-------------------|
| `rule_added` | A rule is created | `type`, `valueType`, `value` |
| `rule_removed` | A rule is deleted | `type`, `valueType`, `value` |
| `mode_changed` | A direction's mode changes | `from`, `to` |
| `scope_deleted` | A pod or inbox is deleted, cascade-deleting its policy | `inboundMode`, `outboundMode`, `removedRules` |
| `send_rejected` | Outbound policy refuses a send | `rejectedRecipient`, `reason`, `matchedScope` |
| `inbound_rejected` | Inbound policy refuses delivery | `rejectedSender`, `reason`, `matchedScope` |

Each event also carries its scope, the direction where one applies, and the console user who made the change. The two rejection actions have no actor — they are written by the enforcement path, not a person.

`scope_deleted` exists because deleting a pod or inbox cascade-deletes its policy, which would otherwise make the cheapest way to remove a restriction the only untracked one.

`inbound_rejected` matters most because a refused delivery has no other trace: policy-dropped mail is accepted at SMTP and discarded, so the recipient never sees it and the sender gets no bounce.

Both rejection actions are deduplicated to **one row per inbox and correspondent per hour**, so an agent retrying a blocked recipient in a loop — or an outside sender doing the same — cannot flood the trail.

Read it in the console under **Allow/Block List → History**, or over the API:

```bash
curl -H "Authorization: Bearer $OPENMAIL_API_KEY" \
  "https://api.openmail.sh/v1/policy/audit?action=send_rejected,inbound_rejected&since=2026-08-01T00:00:00Z"
```

## API reference

All policy endpoints require an **account-wide** API key. Scope is selected with `?podId=` or `?inboxId=`; neither means the account scope.

| Method | Path | Purpose |
|--------|------|---------|
| `GET` | `/v1/policy` | Read a scope's modes, own rules, and inherited rules |
| `PUT` | `/v1/policy` | Declaratively set modes and replace rules — for provisioning |
| `PUT` | `/v1/policy/mode` | Set one direction's mode |
| `POST` | `/v1/policy/rules` | Add one allow/block rule |
| `DELETE` | `/v1/policy/rules/:id` | Remove a rule |
| `GET` | `/v1/policy/audit` | Read the audit trail |

### Provision a boundary in one call

`PUT /v1/policy` is the endpoint to automate against. It sets modes and **replaces** the scope's own rules for any direction you include, so re-running it converges to the state you declared rather than accumulating rules. Omitted directions are left untouched; pass `[]` to clear a direction's rules.

The whole body is validated before anything is applied, so a bad outbound section cannot leave an already-applied inbound section behind.

```bash
curl -X PUT "https://api.openmail.sh/v1/policy?inboxId=$INBOX_ID" \
  -H "Authorization: Bearer $OPENMAIL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "inbound":  { "mode": "allowlist", "rules": [{ "type": "allow", "value": "partner.com" }] },
    "outbound": { "mode": "allowlist", "rules": [
      { "type": "allow", "value": "support@partner.com" },
      { "type": "allow", "value": "ops@partner.com" }
    ]}
  }'
```

Up to 500 rules per direction per call.

### Read what is actually in force

`GET /v1/policy` returns the scope's own modes and rules **and** what it inherits, so you can see the effective boundary without walking the chain yourself:

```json
{
  "scope": "inbox",
  "rules": [],
  "inheritedRules": [],
  "modes": {
    "inbound":  { "mode": "inherit",   "inheritedMode": "allowlist", "inheritedSource": "account" },
    "outbound": { "mode": "allowlist", "inheritedMode": "none",      "inheritedSource": "default" }
  }
}
```

`rules` are set on this scope; `inheritedRules` come from the pod and account. An inherited rule can only be removed by addressing the scope that owns it — deleting one from a child scope returns `403 inherited_rule`.

### Audit query parameters

| Parameter | Notes |
|-----------|-------|
| `action` | Comma-separated: `rule_added`, `rule_removed`, `mode_changed`, `scope_deleted`, `send_rejected`, `inbound_rejected`. An unknown name is a `400`, not a silent no-op. |
| `direction` | `inbound` or `outbound` |
| `podId` / `inboxId` | Events recorded **at** that scope, matched exactly — an inbox filter does not sweep in the account changes it inherits |
| `since` / `until` | ISO-8601. `since` inclusive, `until` exclusive. An unparseable value is a `400`. |
| `limit` / `offset` | Page size 1–100, default 50. The response carries an unpaginated `total`. |

## Worked example

One pod per customer tenant, one inbox per agent. The account sets a floor nobody can escape, the pod narrows it to that tenant, the inbox narrows it to one counterparty.

```bash
# 1. Account floor: block a domain everywhere. No pod or inbox can undo this.
curl -X POST "https://api.openmail.sh/v1/policy/rules" \
  -H "Authorization: Bearer $OPENMAIL_API_KEY" -H "Content-Type: application/json" \
  -d '{ "type": "block", "value": "known-bad.example", "direction": "outbound" }'

# 2. Pod: this tenant's agents may only correspond within the tenant's domain.
curl -X PUT "https://api.openmail.sh/v1/policy?podId=$POD_ID" \
  -H "Authorization: Bearer $OPENMAIL_API_KEY" -H "Content-Type: application/json" \
  -d '{
    "inbound":  { "mode": "allowlist", "rules": [{ "type": "allow", "value": "tenant.com" }] },
    "outbound": { "mode": "allowlist", "rules": [{ "type": "allow", "value": "tenant.com" }] }
  }'

# 3. Inbox: this one agent talks to exactly one mailbox.
curl -X PUT "https://api.openmail.sh/v1/policy?inboxId=$INBOX_ID" \
  -H "Authorization: Bearer $OPENMAIL_API_KEY" -H "Content-Type: application/json" \
  -d '{ "outbound": { "mode": "allowlist", "rules": [{ "type": "allow", "value": "ap@tenant.com" }] } }'

# 4. Mint the agent's key. It can read and send from this inbox — and nothing else.
curl -X POST "https://api.openmail.sh/v1/inboxes/$INBOX_ID/api-keys" \
  -H "Authorization: Bearer $OPENMAIL_API_KEY" -H "Content-Type: application/json" \
  -d '{ "name": "invoice-agent" }'
```

The agent now holds a key that can send only from its inbox, only to `ap@tenant.com`, and never to `known-bad.example`. It cannot read the policy, cannot change it, and cannot mint a broader key. Every attempt to reach outside that set is refused synchronously and recorded.

## Managing rules in the console

Go to **Allow/Block List** in the [Dashboard](https://console.openmail.sh/login). From there the account owner can:

- Add email addresses or domains to the allow or block list, per direction
- Switch each direction's mode between `none`, `allowlist`, and `inherit`
- Remove rules owned by the scope being viewed
- Read the **History** tab — the audit trail

Members see the same page read-only.

## Limits and known behaviour

- **Domain rules do not match subdomains.** `example.com` covers `bob@example.com` but not `bob@mail.example.com`. Add each domain you mean to cover.
- **No wildcards or regular expressions.** A rule is an exact address or an exact domain.
- **Rules are address-based only.** There is no policy on subject, body content, or attachment type.
- **Denied inbound mail is dropped silently** — no bounce, no notification, no quarantine view. It is recorded as an `inbound_rejected` audit event, so the drop is visible to you even though it is invisible to the sender.
- **A value cannot be in both allow and block for the same direction at the same scope.** Block would always win, leaving the allow silently dead, so the API rejects it with `409`. Across *different* scopes it is permitted, and block still wins.
- **No dedicated policy-admin role.** Roles are `owner` and `member`; policy changes are owner-only.
- **No plan gating.** Sender rules are available on every plan.

<Tip>
  Sender rules work alongside [suppressions](/concepts/suppressions). Suppressions automatically block addresses that have bounced or been reported as spam. Sender rules give you manual control on top of that.
</Tip>
